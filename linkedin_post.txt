====================================================
LINKEDIN POST — EVENT-SOURCED CORE BANKING
====================================================

A few weeks ago, I started building something I've wanted to dig into for a long time:
a core banking ledger system. Not a tutorial clone, but a system designed around
real production patterns: Event Sourcing and CQRS.

These concepts weren't entirely new to me. I'd come across them in passing, but never
sat down to truly understand them until I attended a webinar hosted by Esco Obong for
Algorythm, where Niran Fajemisin broke down the ideas in a way that finally clicked.
That talk turned into a spark, and the spark turned into this project.

What started as a learning exercise to understand the basics quickly grew into something
more serious. As I went deeper, I kept finding problems worth solving and solving them
properly. Here's where it ended up:

1. The Outbox Pattern for guaranteed event delivery, ensuring that when a command
   succeeds, the downstream read projections always get notified, even if Kafka
   is temporarily unavailable.

2. Kafka-driven live projections, where read models update asynchronously as events
   flow through the system, giving the query side a live, eventually-consistent
   view of account state without touching the write model.

3. Projection gap handling and manual rebuild/replay tooling, so if a projection
   ever falls behind or becomes inconsistent, you can rebuild it cleanly from the
   event store, the single source of truth, without any data loss.

4. Hot account concurrency hardening. After running a load test that hammered the
   system with concurrent deposits and withdrawals on the same accounts, I found
   real contention issues. The fix involved per-account in-process mutexes,
   server-side retry logic with exponential backoff, and snapshot interval tuning
   to keep aggregate loads fast under pressure.

The deeper I went, the more I realised these aren't just academic patterns. They
solve real, gnarly problems that show up in financial systems at scale.


====================================================
WHY EVENT SOURCING?
====================================================

Event Sourcing stores every change as an immutable fact rather than overwriting state.
That single shift unlocks a lot. Let me tie each benefit to how this project actually
works.


1. Audit trail by default.

In a typical CRUD system, when you withdraw money you update a balance column.
The old value is gone. If a customer calls in six months asking why their balance
dropped, you are digging through application logs hoping something was captured.

With Event Sourcing, every action produces a named, timestamped event that is
appended to the store and never modified. In this project, an account's life
looks like this in the database:

   version 1 — AccountCreated    (ownerId: user-1, currency: NGN)
   version 2 — MoneyDeposited    (amount: 15000, transactionId: txn-1)
   version 3 — MoneyDeposited    (amount: 25000, transactionId: txn-2)
   version 4 — MoneyWithdrawn    (amount: 5000,  transactionId: txn-3)
   version 5 — AccountFrozen     (reason: compliance review)

That is the full history. Nothing was overwritten. The event store is the audit log.


2. Full history and time travel.

Because the events are all there, you can replay them up to any point and know
exactly what the account looked like at that moment. What was the balance before
that last withdrawal? Replay events 1 through 3. When was this account frozen and
why? It is right there in the stream.

In a banking context this is not a nice-to-have. Regulators, compliance teams,
and dispute resolution all depend on being able to answer these questions with
certainty.


3. The aggregate and how state is actually rebuilt.

This is where it gets concrete. There is no "balance column" in this system.
The aggregate is a class that holds state in memory and rebuilds it by replaying
events. Here is a simplified version of how the AccountAggregate handles incoming
events:

   protected when(event: DomainEvent): void {
     switch (event.type) {
       case 'AccountCreated':
         this.accountId = event.accountId;
         this.ownerId   = event.ownerId;
         this.currency  = event.currency;
         this.status    = 'ACTIVE';
         this.balance   = 0;
         break;

       case 'MoneyDeposited':
         this.balance += event.amount;
         break;

       case 'MoneyWithdrawn':
         this.balance -= event.amount;
         break;

       case 'AccountFrozen':
         this.status = 'FROZEN';
         break;
     }
   }

When a command comes in, the repository loads the full event stream for that
account and calls loadFromHistory(), which feeds every past event through when().
By the end of replay, the aggregate holds the correct current state, built purely
from facts, with no mutable rows involved.


4. Snapshots keep replay fast.

Replaying from event 1 every single time works fine for a new account. But an
account with 5000 transactions would be painfully slow to rehydrate on every
command. That is where snapshots come in.

Every 50 events, the system saves a snapshot: a serialized copy of the aggregate's
state at that version. The next time the account is loaded, the repository:

   a. Fetches the latest snapshot (say, at version 4950)
   b. Restores the aggregate to that state
   c. Reads only the events after version 4950 from the store
   d. Replays just those tail events

The snapshot is purely a performance optimization. The event stream remains the
source of truth. If you deleted every snapshot, the system would still work
correctly, just more slowly.


5. Fast reads through CQRS, with an honest tradeoff.

The write side and the read side are completely separate. Commands go through the
aggregate and the event store. Queries never touch any of that. They read from
pre-built projection tables like account_summary and account_statement, which are
flat, denormalized, and optimized for lookups.

The tradeoff is that projections update asynchronously. A read immediately after
a write may reflect the previous state for a few milliseconds while the event
travels through the outbox and Kafka to update the read model. That lag is real,
it is intentional, and it is acceptable. The write already succeeded. Consistency
follows shortly after.


6. Better concurrency without blocking locks.

A traditional system handling two simultaneous withdrawals on the same account
often reaches for a pessimistic lock: lock the row, let one operation through,
make the other wait. Under load this becomes a bottleneck.

This project uses optimistic concurrency instead. Every event append includes an
expected version number. If two operations race, the event store checks: is the
current stream version what you expected? If not, you get a WrongExpectedVersionError
and the operation retries. No blocking. No waiting behind a lock. The system
stays responsive and the aggregate stays consistent.


7. Read models are disposable.

If a bug corrupts a projection or a new business requirement needs a different
read model entirely, you do not patch rows or write a migration to fix derived
data. You delete the projection and replay from the event store. The source of
truth is intact and always has been. This is exactly what the rebuild endpoints
in this project do.


8. The domain speaks in business language.

Events like AccountCreated, MoneyDeposited, MoneyWithdrawn, and AccountFrozen
map directly to how a banking team thinks and talks. The code is not a set of
INSERT and UPDATE statements. It is a record of things that actually happened.
That alignment between the domain model and the business vocabulary makes the
system significantly easier to reason about and extend.


====================================================
HIGH-LEVEL FLOW
====================================================

The architecture splits into two distinct paths: the write side for commands and
the read side for queries. Here is how a real operation moves through the system.


The Write Path: taking a command from HTTP to the event store.

Before any domain logic runs, the first gate is idempotency. Every command endpoint
in this system requires an Idempotency-Key header, a UUID the client generates and
attaches to the request. The server checks this key against a Postgres-backed
idempotency store before doing anything else.

If the key is new, the request proceeds. If the key has been seen before with the
same payload, the server returns the original response without re-executing the
command. If the same key arrives while the first request is still in flight, the
server returns a conflict immediately. This protects against the classic retry
problem: a client sends a deposit, the network drops the response, the client
retries, and the deposit runs twice. With idempotency keys, the retry is safe.

For deposits and withdrawals there is a second layer underneath: the transactionId
field on the request body. Even if a caller somehow rotates their Idempotency-Key
on a retry, reusing the same transactionId will not produce a second money movement.
The Idempotency-Key protects the transport layer. The transactionId protects the
business transaction. Both are necessary, and they operate independently.

With idempotency confirmed, the request is handed off to the command handler.
The command handler calls the repository, which is responsible for loading the
account aggregate.

Loading the aggregate works in two steps. First, the repository checks if a
snapshot exists for that account. If it does, it restores the aggregate to the
state captured in that snapshot. Then it reads only the events that occurred after
the snapshot version and replays those tail events through the aggregate.
With the aggregate fully hydrated, the domain logic runs: check the account is
active, check the balance covers the withdrawal if applicable, check for duplicate
transaction IDs. If everything passes, the aggregate emits a new event.

That event is then appended to the event store with an expected version number.
The event store checks whether the current stream version matches what the handler
expected. If another request modified the account in the window between loading and
saving, the versions will not match and the operation retries. This is the
optimistic concurrency mechanism.

Here is what the command handler looks like in this project:

   async execute(command: DepositMoneyCommand): Promise<void> {
     await this.repository.executeWithRetry(command.accountId, (account) => {
       account.deposit(
         command.amount,
         command.currency,
         command.transactionId,
         command.context,
       );
     });
   }

The executeWithRetry wrapper handles per-account locking within a single process
instance and the retry loop for cross-instance conflicts. The handler itself stays
clean.


Reliable delivery through the transactional outbox.

Appending to the event store is not enough on its own. Downstream systems need to
know something happened, but publishing directly to Kafka inside the same operation
is a dual-write: if the database commit succeeds but the Kafka publish fails, the
read model never updates.

The outbox pattern solves this. In the same database transaction that persists the
event, a record is written to an outbox table. A separate relay process polls the
outbox and publishes those records to Kafka. Because the outbox write and the event
append are in the same transaction, they either both succeed or both fail. Kafka
delivery is decoupled from the write operation and guaranteed to eventually happen.


The Read Path: fast lookups from projections.

On the read side, things are deliberately simple. A Kafka consumer picks up the
published events and updates the projection tables: account_summary for current
account state and account_statement for the transaction history. When a client
queries an account, the query handler reads directly from those tables. No
aggregate loading, no event replay, just a fast lookup against a flat,
denormalized row.

The read model is eventually consistent with the write side, updated asynchronously
as events flow through Kafka. For most operations, the lag is milliseconds. That
is an explicit and accepted tradeoff for the performance and separation of concerns
that CQRS provides.


Manual replay: when projections need rebuilding.

There is one more path worth calling out. If a projection falls behind, gets
corrupted, or needs to be rebuilt from scratch because of a bug fix or a new
requirement, the system can bypass Kafka entirely and replay events directly from
the event store. This gives you the complete history needed to reconstruct any
read model from the ground up, independent of what Kafka has or has not retained.
The event store is always intact. That is the whole point.


====================================================
WHEN THE SYSTEM BROKE: THE LOAD TEST STORY
====================================================

Once the core system was in place, I ran a load test to see how it held up under
realistic pressure. Not a simple benchmark, but a scenario-driven run that
mimicked real banking traffic: a mix of deposits, withdrawals, balance reads,
and history lookups, concentrated on a hot subset of accounts.

The configuration was 50 concurrent workers running continuously for 120 seconds,
hitting 250 accounts where 90% of all write traffic was directed at just 5% of
those accounts, roughly 12 to 13 accounts absorbing almost all the writes.
This is not an unusual pattern in financial systems. Merchant accounts, shared
wallets, and high-volume accounts see this kind of concentration every day.

The results were not good:

   Total requests:   19,404
   Failed requests:   2,428
   Failure rate:     12.5%

   Deposit 409s:      1,026
   Withdrawal 409s:     977

Almost all of the failures were 409 Conflict responses. The optimistic concurrency
mechanism was working exactly as designed: detecting a version mismatch and raising
an error. But the system had no recovery path. Every request that lost a race
became a permanent failure returned to the client. Under that level of hot-account
pressure with 50 workers, that outcome was unavoidable.

There were two compounding problems underneath this.

The first was the absence of server-side retry. Optimistic concurrency tells you
a conflict happened. It does not tell you the operation was wrong. A deposit and
a withdrawal both racing on the same account are two valid, independent commands
from different clients. The correct response to losing the race is to reload the
aggregate and try again, not to reject the request outright.

The second was that all 50 workers were loading the aggregate before any database
lock was acquired. Three workers could each load account acc-8 at version 10
at the same time. One would write and move the stream to version 11. The other
two would then fail on their version check at the database level, even though all
three operations were perfectly valid.

The fixes were four targeted changes:

1. Server-side retry. The load-execute-save cycle was wrapped in an executeWithRetry
   method. On a WrongExpectedVersionError, the aggregate reloads and retries up
   to three times with a small random delay between attempts. Domain errors like
   insufficient funds propagate immediately. Only infrastructure conflicts trigger
   the retry.

2. Per-account in-process mutex. A promise-chaining lock was added so that concurrent
   requests for the same account within the same process are serialised before they
   even reach Postgres. Workers queue up instead of all loading stale state at once.

3. Snapshot interval halved from 100 to 50 versions. Hot accounts were accumulating
   events fast and replaying long tails on every write. Snapshotting more frequently
   kept the tail replay short regardless of how quickly the stream grew.

4. Outbox poll interval reduced from 1000ms to 200ms. A 1 second polling gap meant
   that reads arriving shortly after an account was created would get 404s because
   the projection had not caught up yet. Shrinking the poll window significantly
   reduced that lag.

After those changes, the same load test run produced this:

   Total requests:   19,195
   Failed requests:     381
   Failure rate:      ~2%

   Deposit 409s:          0
   Withdrawal 409s:       0

Write failures went to zero. The remaining failures were 404s on reads that arrived
before the projection had caught up, which is expected behaviour under eventual
consistency and not something that warrants a 500.

What made this worthwhile was that none of these fixes were architectural rewrites.
They were precise, targeted changes to the right places in the system. That is
only possible when the system has clear boundaries and the source of truth is never
in doubt.


====================================================
WHEN NOT TO USE EVENT SOURCING
====================================================

Event Sourcing is genuinely powerful, but it is not the right choice for everything.
It is worth being honest about where it earns its complexity and where it does not.

You are taking on more moving parts. An event store, a snapshot store, projection
tables, an outbox, a message broker, and consumers are all part of this system.
A traditional CRUD application with a single database is far simpler to build,
deploy, and operate. If your domain does not need full history, temporal queries,
or the ability to rebuild read models from scratch, that simplicity is the right call.

Eventual consistency is harder to reason about than immediate consistency, and
significantly harder to explain to stakeholders. In a CQRS system, a read right
after a write may not yet reflect the write. Most of the time that lag is
milliseconds and acceptable. But it has to be understood by everyone touching
the system, from engineers to product teams to the QA person writing test cases.

Querying event-sourced data requires deliberate design. In a relational system
you can write a quick JOIN to answer a new business question. In an event-sourced
system, if the answer is not already captured in a projection, you either build
a new projection or replay the event store. Neither is as fast as adding a query.

The pattern earns its weight when the problem genuinely calls for it. Full audit
history that can be enforced at the infrastructure level rather than bolted on
later. The ability to recover from bad deployments by replaying events into a
corrected read model. Domains where the sequence of things that happened matters
as much as the current state. Financial systems sit squarely in that category.
Not every system does.


====================================================
WHAT IS NEXT
====================================================

The system works well as a single-account ledger but there is still meaningful
ground to cover before it reflects the full picture of a production banking backend.

Read-your-own-write.

Right now, a write returns the moment the event is appended to the event store.
The read model updates asynchronously. That tradeoff is intentional and the
eventual consistency lag is usually milliseconds. But for a client that writes
and immediately reads back the result, there is a window where the query returns
stale data.

The fix is a read-your-own-write strategy: after a command succeeds, the response
includes the version the account is now at. When the client queries immediately
after, it can pass that version as a hint. If the projection has not yet reached
that version, the query handler falls back to rehydrating directly from the event
store. The client always sees at least the state it just wrote, without breaking
the separation between the write and read sides for everyone else.

The durable transfer saga.

Account-level operations like deposits and withdrawals are fully implemented.
Transfers between two accounts are scaffolding only. The reason is that a transfer
is not a single command. It touches two aggregates across a sequence of steps:
debit the source account, credit the destination account, handle the cases where
either step fails.

This is the classic distributed transaction problem and the right solution is a
saga, a process manager that tracks the transfer through its states using events.
If the debit succeeds but the credit fails, the saga issues a compensating event
to reverse the debit. Each step is durable and recoverable because the state of
the saga itself is stored as events. This is one of the areas where Event Sourcing
pays off most clearly.

Once the saga is in place, a transfer status projection and query endpoint follow
naturally. Clients need to be able to ask: what is the current state of this
transfer? Did it complete, fail, or is it still in progress?

Observability.

The system currently has no monitoring on the outbox lag, Kafka consumer lag, or
projection failures. In production, these are the first things that tell you
something is wrong before users start reporting it. Metrics on how far behind the
outbox publisher is, how many events are waiting in Kafka, and whether any
projection updates are failing would make the system genuinely operable rather
than just functional.

Integration tests.

The most meaningful test coverage for a system like this would target the
scenarios that are hardest to reason about: concurrent write conflicts and their
retry behaviour, projection gaps and rebuild correctness, and the idempotency
and transaction deduplication paths exercising edge cases like in-flight retries
and payload mismatches. Unit tests cover individual pieces. Integration tests
covering these flows would close the loop on the full system behaving correctly
under realistic conditions.


====================================================
CONCLUSION
====================================================

Building this project taught me more than I expected, and some of the most
valuable lessons came from the parts I initially thought were unnecessary.

The outbox pattern was the clearest example of that. When I first added it, it
felt like overkill. The system was already writing events to the store. Why add
another table, another polling process, another layer just to get those events
into Kafka? The answer became obvious the moment I simulated Kafka being
unavailable. Without the outbox, a Kafka failure during a write means the event
is persisted but the read model never hears about it. The write side and the read
side silently diverge with no recovery path. With the outbox, the event sits
safely in the database until the broker comes back and the publisher picks it up.
The outbox does not feel like overkill once you have seen what happens without it.

The other lesson that stuck was how fundamentally different recovery feels in an
event-sourced system. In a traditional database, a corrupted or inconsistent read
model is a real problem. You might have lost data, or have no clean way to
reconstruct what the correct state should have been. In this system, the event
store is always intact. If a projection is wrong, you delete it and replay. The
correct state is derived from the facts that were recorded, every single one of
them, in order, untouched. That is not just an architectural nicety. It changes
how you think about failure. Recovery stops being a crisis and becomes a procedure.
